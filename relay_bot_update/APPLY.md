# 相手環境での適用手順

1. 相手側の本人がこの更新元のGitコミットまたはタグを確認し、`python3 tools/stage2/relay_bot_update.py verify-manifest relay_bot_update` でMANIFEST.jsonのSHA-256を照合する。
2. 対象の実行環境、リポジトリ、サービス名を確認する。名前やパスが一致しない場合は中止して予定ばんへ報告する。
3. 本人の承認後、設定・秘密・履歴・処理済み番号を変更せず、対象ファイルだけ控えに複製する。
4. `runtime.py` を相手側の既存の呼びかけ判定・返事記録へ移植し、同梱の架空データ試験（`cd relay_bot_update && python3 -m unittest`）を実行する。実データを試験に使わない。
5. 相手側本人が適用と再起動を承認した場合のみ実施する。予定ばんから遠隔実行しない。
6. 結果をRESULT.schema.jsonの形式で返す。失敗時は相手側の本人がROLLBACK.mdに従う。

## 架空データの確認観点

- 呼びかけ印なしのグループ発言でAI・担当ボットが起動しない。
- 同じメッセージIDが複数経路から届いても返事は一度だけ。
- 現在時刻が本人の時間帯で判定器へ渡る。
- 印のない本人宛て依頼は通常経路を維持する。

返事台帳はMac側・連携ボット側の経路が同じSQLiteファイルを使える構成に置く。本文・送り手・会話履歴は台帳に入れない。送信結果が不明なら予約を保持して照合し、確実な送信失敗が分かった場合だけ予約を解放する。SQLiteの置き場を経路間で共有できない環境では、適用前に相手側の本人へ未対応として報告し、別々の台帳で二重防止できると扱わない。
