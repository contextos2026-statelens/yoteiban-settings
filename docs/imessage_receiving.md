# iMessage受信経路の設計・導入

## 経路の選択

| 会話 | 正とする受信元 | 条件 |
|---|---|---|
| 利用者本人のMessagesアカウントに届く1対1・グループ | Mac `chat.db` | DBに存在するものだけ。読み取り専用で取得 |
| 連携ボット番号への1対1 | Linq webhook | `message.received`、inboundのみ |
| 利用者本人が参加せず連携ボットだけが参加するグループ | Linq webhook | Linqの最新参加者一覧で本人が不在、連携ボットオーナーが在籍 |
| 本人も参加するグループのLinq複製イベント | Mac `chat.db` | Macを正とし、Linq側は破棄 |

Mac側では `is_from_me` を入力から除外する。Linqでは `direction=outbound` を同様に除外する。Linqの1対1はLinq番号宛てのアカウント所有チャットに限定する。表示名だけでは会話を対応づけない。

Linqのchat list / chat retrieve APIはチャットID、`is_group`、handlesと参加状態（`is_me`、`left_at`、status等）を返す。message webhookだけで参加者全員が分からない場合はチャット詳細を取得する。参加者追加・削除イベント後に一覧を更新する。ID対応または名簿が不明・古い・不整合なら `hold` にして処理せず、再取得・確認へ回す。所属変更後の履歴を現在の名簿から推測しない。

## 重複・欠落

1. 主な重複対策は経路選択で、同じ参加者集合のグループは本人が在籍すれば常にMac側を正にする。名簿不明時は処理を保留する。
2. 同一経路の再送は、Macのmessage GUID（無い場合rowid）とLinqのevent/message IDで排除する。保存済み履歴は消さず、カーソルを独立して管理する。
3. 別経路IDしか無い場合、内容・時刻・参加者を正規化した候補指紋で照合できる。ただし同じ内容を連続送信した正当な別メッセージの可能性があるので、この指紋だけで自動破棄しない。曖昧なら保留・照合する。
4. webhook event IDとsource cursorを永続化し、受信成功前にcursorを進めない。復旧後は利用可能な履歴APIまたはchat.dbカーソルから空白期間を補う。履歴取得に失敗・非対応なら接続状態を `degraded` とし、「受信できた」と報告しない。

## 接続準備と状態

設定回答（使う経路・同意）と接続状態を別々に保存する。状態ファイルはGit外の所有者限定private stateに置き、回答・接続状態を既存ファイルに追記するだけにする。設定例や公開コードにはアカウント、番号、チャットID、本文、鍵、Webhook URLを入れない。

1. 許可後に既存のMac watcher、Linq webhook listen、予定ばんの受け口・台帳を検査する。すでにあるlistenerやconsumerを重ねて起動しない。
2. 必要な経路だけを選び、既存コードを再利用して設定差分を作る。初期状態は停止/影運用。既存サービス設定を上書きしない。
3. Mac本人がMessagesへサインインし、実際のreader実行ファイルにフルディスクアクセスを許可する。Linq本人の認証・webhook登録も本人が確認する。これらの権限付与やサインインは自動化しない。
4. 架空メッセージで解析、from-me除外、グループ振り分け、同一イベント再送、曖昧指紋保留、cursor復帰を検証する。本文・鍵はログに出さない。
5. 本人の明示許可後、対象の1対1または合意済みグループでテストメッセージを送り、sourceイベントID、受け口受信、台帳の1件化、返信の最大1回を確認する。実機の新着が確認できた後だけ接続を `connected` とする。
6. 本番切替は別途本人の承認後。停止中の片側経路を代替扱いにしない。バックフィル可否・保持期間は実機/契約APIで確かめ、未確認なら欠落期間を明示する。

## このリポジトリの実装範囲

`redesign/mac/yoteiban_watch` は汎用の読み取りprototype。iMessageの読取とローカルsource ID重複排除を持つ。`core/yoteiban_core/imessage_routes.py` はfail-closedな経路判定、`receiver_status.py` は回答と接続状態の分離保存、watcherの `normalize_linq_webhook` はLinqイベントの共通形式化を担う。これらだけではLinq listener、最新名簿取得、履歴バックフィル、予定ばん本番受け口への接続は完了しない。導入前に既存の連携ボットrelayと予定ばん受け口へ適合するadapterを別途結び、架空・実機の両試験を行う。

## 連携ボット発言の除外

`config.json` の `relay_bots` は空配列を既定とする。利用者がprivate configにボットごとの `label`、`sender_handles`、`call_markers`、`reply_markers`、`owner`（`self` / `family`）を設定した場合だけ働く。呼びかけ印は本文先頭のみ、発言印は本文内、送り主は識別子一致で判定する。分類されたイベントはsorter・AI・受け口へ送らず、状態DBに種別ごとの累計件数だけを保存する。印が設定されていない場合、通常の取り込みに影響しない。特定の印や相手の識別子をソースコードへ固定しない。
